Grid search

This document is the reference for the per-strategy grid-search optimisation loop. It covers the YAML schema, the available objectives (including the custom cagr_mdd_hybrid), the CLI workflow, and the threading invariants that keep parallel runs honest under polars + multiprocessing.

1. Why a full grid

Three of the four common search axes are categorical (lookbacks_days families, rebalance cadence, allocation_rule, top_n) and the one continuous knob (momentum_delta_threshold_pct) is naturally discretised to ~21 sweep points. With the max_combinations: 2000 guard refusing accidental explosion, exhaustive enumeration finishes in single-digit minutes on a 24-core workstation. Bayesian / TPE surrogates pay off when each evaluation is expensive (minutes-hours) and the space is dominated by continuous dimensions — that is not this problem. The per-combo callable is small enough that swapping the cartesian-product loop for an Optuna study is a future-proof exercise: the worker signature does not change.

2. YAML schema

2.1 Shared block — shared.optimization

shared:
  optimization:
    keep_top_k: 5             # rows persisted to data/optimized.yaml per run
    max_combinations: 2000    # explosion guard; --force bypasses
    cagr_mdd_hybrid:
      cagr_tolerance_pct: 15
      mdd_tolerance_pct: 15

keep_top_k and max_combinations apply to every strategy's grid run — they govern the pipeline plumbing, not the search axes, so they live on the shared block. The cagr_mdd_hybrid tolerances are the defaults for the hybrid objective; a strategy can override either tolerance inline under its own optimize: block.

2.2 Per-strategy block — optimize:

strategies:
  - name: hex_lev_grow
    # ... regular strategy fields ...
    optimize:
      axes:
        lookbacks_days:
          choices:
            - [126]
            - [252]
            - [21, 63, 126]
            - [42, 84, 168]
            - [63, 126, 252]
        rebalance:
          choices: [weekly_sunday, monthly_first_sunday]
        momentum_delta_threshold_pct:
          min: 0.0
          max: 10.0
          step: 0.5
        top_n:
          choices: [1, 2, 3, all]
      objective: cagr_mdd_hybrid
      # Optional inline overrides of the shared cagr_mdd_hybrid tolerances.
      # cagr_tolerance_pct: 10
      # mdd_tolerance_pct: 20

2.3 Field reference

Field Required Notes
axes: yes Dict of axis-name → axis-spec. Axis names must be a subset of OPTIMIZABLE_AXIS_NAMES (lookbacks_days, rebalance, momentum_delta_threshold_pct, allocation_rule, top_n); typos fail at config-load.
axes.<name>.choices: one of Explicit value list. For lookbacks_days each choice is itself a list (e.g. [63, 126, 252] for ADM 3/6/12).
axes.<name>.{min,max,step}: one of Arithmetic progression with both endpoints inclusive. Step must be > 0 and min <= max.
axes.top_n.choices: — Accepts the literal string "all" alongside ints; resolved to len(asset_ids) at run time.
objective: yes One of sharpe, cagr, calmar, sortino, cagr_mdd_hybrid.
cagr_tolerance_pct: optional Per-strategy override of the shared cagr_mdd_hybrid CAGR tolerance (in pct, e.g. 15 = 15%).
mdd_tolerance_pct: optional Per-strategy override of the shared cagr_mdd_hybrid MaxDD tolerance.

keep_top_k and max_combinations are not per-strategy fields — they live on shared.optimization (see §2.1). Putting either inside a strategy's optimize: block raises a clear error at config-load.

3. CLI workflow

# 1. Run the grid for one strategy. Top-K rows get written to data/optimized.yaml.
poetry run pea-mom optimize hex_lev_grow

# 2. Inspect the persisted top-K (or scope to one strategy).
poetry run pea-mom show-optimized
poetry run pea-mom show-optimized hex_lev_grow

# 3. Backtest with the rank-1 optimized params overlaid (default = rank 1).
poetry run pea-mom backtest --use-optimized
# Or pick a different rank.
poetry run pea-mom backtest --use-optimized 3

# 4. Render the dashboard. Strategies that received an overlay show a
#    🎯 r<N> badge next to their name and their displayed Scoring /
#    Allocation / Band cells reflect the overlaid values.
poetry run pea-mom render

# Or do it all at once:
poetry run pea-mom run --use-optimized

The optimize engine writes to data/optimized.yaml; the backtest --use-optimized flag persists the per-strategy applied-rank map to data/results/applied_optimized.json for the renderer to pick up. Rendering without an overlay (i.e. after running plain pea-mom backtest) reverts the table to the YAML-configured params and drops the badge — there is one source of truth per page.

4. Objectives

Single-metric objectives sort the rows by their named metric in descending order. NaN / None / non-finite values are pushed to the end of the ranking so the top-K never surfaces an undefined-ratio row.

4.1 sharpe, cagr, sortino

Straightforward: highest first.

4.2 calmar

calmar = cagr / |max_drawdown|. Highest first; rows with zero MaxDD have an undefined ratio and are pushed to the end.

4.3 cagr_mdd_hybrid

A two-knob objective designed around a specific intuition: prefer the highest CAGR, unless a meaningfully-close challenger has materially better drawdowns. Operationalised as:

Given two candidates A (CAGR leader of the current pool) and B (challenger), B replaces A iff

  1. B.cagr ≥ A.cagr * (1 - cagr_tolerance) — B's CAGR is within cagr_tolerance_pct of the leader (default 15%), AND
  2. |B.MaxDD| ≤ |A.MaxDD| * (1 - mdd_tolerance) — B's drawdown is at least mdd_tolerance_pct smaller than the leader's (default 15%).

For a full top-K ranking, the rule is applied iteratively: pick #1 from the pool, remove it, recompute the leader of the remaining rows, pick

2 by the rule against the new leader, and so on.

Worked example

Two candidate rows on the same universe:

Row CAGR MaxDD
A 11% -20%
B 9.5% -10%

With cagr_tolerance_pct: 15 and mdd_tolerance_pct: 15:

  • B's CAGR is 9.5/11 = 86.4% of the leader's, which is within the 15% tolerance.
  • B's |MaxDD| is 10/20 = 50% of the leader's, a 50% reduction — well above the 15% threshold.
  • B wins.

Compared to Calmar (cagr / |MaxDD|), the hybrid rule has discrete thresholds rather than a smooth trade-off: a 14% CAGR shortfall with just-better drawdown does NOT win, while a 15% shortfall with much- better drawdown does. This matches the user's intuition that "I want the higher CAGR unless something with similar return is markedly less scary."

Degenerate cases

  • All candidates have non-positive CAGR: the rule short-circuits and returns the CAGR leader (the smallest-|MaxDD| pick under negative CAGR is usually a holds-the-safe-asset run, which the caller can already see directly in the ranked list).
  • Identical MaxDD across the candidate band (e.g. a 100%-equity universe whose drawdown is always the 2008 / 2022 trough): the rule collapses to pure CAGR descent — the band gives nothing to break ties on.

5. Threading and process pool

The engine follows the official Polars multiprocessing user guide verbatim:

  • mp.get_context("spawn") — Polars' Rayon thread pool initialises on first import; calling fork() after that point leaves children with broken-state mutexes and the workers hang silently with 0% CPU. spawn re-imports Polars cleanly in each worker.
  • POLARS_MAX_THREADS=1 per worker — set in the parent process before the pool spins up. Without this, with N workers the total thread count balloons to N × default_thread_count (≈ 24 × 24 on a 24-core box), thrashing the scheduler.
  • max_workers = max(1, os.cpu_count() - 2) — leaves a couple of cores for the OS / interactive shell. Override with --workers N on the CLI.

The worker initialiser receives the prepped prices as parquet bytes (smaller and faster to decode than a pickled DataFrame) and caches them once per process; subsequent combos just re-run the backtest against the cached frame.

6. Output schema — data/optimized.yaml

strategies:
  <strategy_name>:
    ran_at: <ISO 8601 UTC timestamp>
    window:
      start: 2008-08-15
      end: null
    objective: cagr_mdd_hybrid
    n_combinations: 840
    workers: 22
    results:
      - rank: 1
        params:
          lookbacks_days: [252]
          rebalance: weekly_sunday
          momentum_delta_threshold_pct: 10.0
          top_n: 1
        metrics:
          cagr: 0.28993932279348944
          vol_ann: 0.33295190406689656
          sharpe: 0.9164658619181706
          sortino: 0.8474339444761545
          max_drawdown: -0.5218379656089406
          calmar: 0.5556117835450222
          hit_rate: 0.5480263157894737
          final_equity: 90.97358938735874
          n_rebalances: 22
          n_swaps_rejected: 119
      # ... rank 2..K

The file is the union of every strategy's most recent grid run — re-running pea-mom optimize <name> overwrites just that strategy's entry. Existing entries for other strategies survive, so the side-file accumulates results as the user runs the optimiser on different strategies over time.

7. Combinatorial explosion guard

Multiplying the axis cardinalities yields n_combinations. The default cap of max_combinations: 2000 exists to refuse accidental explosions (e.g. forgetting that a step: 0.1 ramp turns 0..10 into 101 points and crosses with 5 other axes). When the cap fires:

strategy 'xxx': grid size 8400 exceeds max_combinations=2000.
Tighten the axes or pass --force.

--force bypasses the check for one-off larger runs; the recommended path for genuinely-larger problems is to raise max_combinations: in YAML so the value is documented alongside the axes.
